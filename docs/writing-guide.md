# 아티클 작성 가이드 (초안)

## 1. 독자와 목표

| 독자 | 글에서 얻어가야 할 것 |
| --- | --- |
| 채용 담당자 | 무엇을 했고, 왜 그렇게 판단했고, 결과가 어땠는지 -- 도입부와 결론만 읽어도 파악 가능해야 함 |
| 개발자 | 재현 가능한 과정, 설정/코드, 실패와 그 원인 |

→ 모든 글은 **"위에서 요약, 아래에서 깊게"** 구조. 첫 문단 + 마지막 섹션만 읽어도 성립해야 한다.

## 2. 토픽 구조

| topic | 성격 | subtopic (안) |
| --- | --- | --- |
| `project-cloud` | 자체 클라우드 구축 학습 프로젝트 (VM 생성부터 순차 진행하는 시리즈) | 시리즈 1개 = subtopic 1개 (예: `build-your-own-cloud`), 편 순서는 `order`. VM → 네트워크 → 스토리지 → 컨트롤 플레인 → DBaaS 같은 단계는 편 제목으로 구분 |
| `ai` | AI 도구 사용기·분석 | `skills`, `models`, `ai-documents` |
| `career`, `outsourcing` | 기존 프로젝트 기록 (유지, 필요 시 보강) | 기존 그대로 |

새 topic/subtopic은 `src/taxonomy.ts`에 먼저 등록해야 빌드가 통과한다.

## 3. 글 유형별 템플릿

### A. Project-Cloud 시리즈 편

```
## 이번 편 요약        -- 목표 / 결과 / 핵심 결정 3줄
## 배경               -- 이전 편에서 이어지는 지점, 왜 이 단계가 필요한가
## 설계               -- 선택지 비교와 선택 이유 (다이어그램 1개 권장)
## 구현               -- 단계별 명령어·설정·코드
## 트러블슈팅          -- 막힌 지점, 원인, 해결
## 실무와의 비교       -- 사내 DBaaS 경험에서 달랐던/같았던 점
## 정리와 다음 편       -- 배운 점, 다음 편 예고
```

### B. AI 분석 (Skill / Model)

```
## 요약               -- 무엇을, 어떤 기준으로 평가했고, 결론은
## 대상과 평가 기준
## 실험 / 사용 사례     -- 프롬프트, 입력, 결과 (재현 가능하게)
## 비교와 분석
## 결론               -- 언제 쓰고 언제 안 쓰는가
```

### 회고 섹션 (선택)

회고는 별도 subtopic이 아니라, 어느 유형의 글이든 끝에 필요할 때만 붙이는 섹션이다. 쓸 만한 게 없으면 생략한다.

```
## 회고               -- 잘된 것 / 아쉬운 것 / 다음에 바꿀 것
```

## 4. 작성 규칙

- **보안**: 회사 DBaaS 관련 내용은 공개된 일반 개념 수준까지만. 내부 시스템명, 구성도, 수치, 고객/코드는 쓰지 않는다.
- **분량**: 시리즈 편·분석글 한국어 기준 3,000~8,000자. 넘치면 편을 나눈다.
- **문체**: About 페이지 말투 기준 -- 1인칭, "~합니다"를 기본으로 "~해요"를 자연스럽게 섞는 대화체. 기술 설명도 옆자리 동료에게 말하듯이.
  - 내가 왜 그걸 했는지, 어디서 헤맸는지, 솔직한 감상("생각보다 오래 걸렸어요", "이건 좀 아쉬웠습니다")을 넣는다.
  - 템플릿의 섹션 제목은 뼈대일 뿐, 실제 제목은 내용에 맞게 자연스럽게 바꾼다 ("트러블슈팅" → "네트워크가 안 붙어서 하루를 날렸다").
- **코드/명령어**: 실행한 그대로, 버전 명시 (OS, 도구 버전은 글 상단 또는 구현 섹션 첫머리).
- **이미지**: `public/assets/blog/<slug>/`에 저장, 다이어그램은 가능하면 소스(mermaid/excalidraw)도 함께 보관.
- **날짜 표현**: "현재", "최근" 대신 구체적 날짜 (예전 글의 "현재(2023.2)" 같은 문제 방지).

### AI 느낌 피하기

AI 검수·번역 후에 아래 항목이 남아 있으면 고친다. 하나하나가 AI의 증거는 아니지만 (사람도 쓰는 표현), 한 글에 몰려 있으면 티가 난다.

**내용**
- 구체적 사실을 일반론으로 뭉개기 -- "다양한 문제가 있었다" 대신 실제로 난 에러, 걸린 시간, 숫자
- 의미 부풀리기 -- 사소한 작업을 "~의 중요성을 보여준다", "시사하는 바가 크다"로 포장
- 주어 없는 피동 -- "~이 요구된다", "~이 고려되었다" → 누가 했는지 쓴다 ("제가 ~했습니다")
- 겹겹이 헤지 -- "~할 수 있을 것으로 보인다" → 확신한 만큼만 단정

**표현 (한국어)**
- 번역투 -- "~를 통해", "~에 있어서", 이중 피동("보여지다"), 긴 관형절 중첩
- 기계적 접속어 -- 문단마다 "또한", "따라서", "이처럼", "한편", "결론적으로"
- 형식명사 남발 -- "~하는 것이다", "~라는 점", "-적/-성/-화" 연쇄
- 괄호 영어 병기 과다 -- 이미 익숙한 용어(가상머신(VM), 네트워크(Network))는 한 번만 또는 생략
- 상투 문구 -- "~에 대해 알아보겠습니다", "~하는 것이 중요합니다", "A가 아니라 B입니다" 식 대비 강조

**구조·리듬**
- 모든 걸 셋씩 나열 (rule of three), "첫째/둘째/셋째"
- 문장 길이·어미가 일정한 단조로운 리듬 -- 짧은 문장, 긴 문장, 혼잣말을 섞는다
- 이야기를 불릿·굵은 글씨·따옴표·대시로 쪼개 강조 -- 경험담은 문단으로
- 과한 이모지·느낌표, 또는 감정이 전혀 없는 보고서 톤

도구: 검수 단계에서 `humanize-korean` 플러그인(`/humanize-scan`, `/humanize-korean`)을 쓴다 (6장 3단계).

참고: [Wikipedia: Signs of AI writing](https://en.wikipedia.org/wiki/Wikipedia:Signs_of_AI_writing), [im-not-ai (한국어 AI 문체 패턴 분류)](https://github.com/epoko77-ai/im-not-ai)

## 5. Frontmatter

```yaml
title: "..."            # 언어별 번역
description: "..."      # 1~2문장, 검색 결과·카드에 노출됨
pubDatetime: 2026-09-23T12:00:00   # 세 언어 동일
topic: "project-cloud"
subtopic: "build-your-own-cloud"
tags: ["kvm", "libvirt"]           # 세 언어 동일, 영문 소문자
coverImage: "/assets/blog/<slug>/cover.png"   # 선택
order: 1                           # 선택. 같은 subtopic 안에서의 순서 (시리즈용)
draft: true                        # 작성 중에는 true
```

## 6. 작업 흐름

1. **이슈 생성** -- 글 1편 = 이슈 1개 (목표 독자, 핵심 메시지, 목차 초안)
2. **한국어 초안** -- `<slug>-ko.md`, `draft: true`
3. **AI 검수 (한국어)** -- 내용 검수와 문체 윤문을 분리해서, 이 순서로 한국어가 완성될 때까지 반복
   1. **내용 검수** (Claude 직접) -- 요약만 읽어도 결론이 전달되는가, 기술적 사실·명령어 오류, 보안 규칙 위반, 맞춤법·중복 문장
   2. **AI 티 스캔** -- `/humanize-scan`으로 본문의 AI 티 정도를 확인. 손볼 게 거의 없으면 다음 단계 생략
   3. **윤문** -- `/humanize-korean`으로 윤문. 호출 시 아래를 함께 지시한다
      - 장르: 개인 기술 블로그, About 페이지 말투(1인칭, "~합니다"+"~해요" 혼용)
      - frontmatter·코드 블록·명령어·링크는 대상에서 제외 (본문 산문만)
      - 긴 글(5,000자 이상)은 섹션 단위로 나눠서 또는 정밀 모드로
   4. **대조 확인** -- 윤문 전후 diff를 직접 읽고, 의미가 바뀌었거나 내 말투가 아닌 부분은 되돌린다. 위 "AI 느낌 피하기" 목록으로 마지막 확인
4. **AI 번역** -- 완성된 한국어본 → `<slug>.md`(en), `<slug>-ja.md`. 코드·명령어·고유명사는 번역하지 않음. 직역보다 각 언어의 자연스러운 블로그 말투로 (영어는 casual first-person, 일본어는 です・ます체)
5. **번역 검수** -- 용어 일관성 확인 후 `draft` 제거
6. **PR → 4321 미리보기 → 머지**
